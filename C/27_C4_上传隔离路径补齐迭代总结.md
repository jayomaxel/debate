# C4 上传隔离路径补齐迭代总结

## 本轮目标

- 补齐上传安全反馈中的“临时隔离路径”要求。
- 让受保护上传在校验前先进入 quarantine 目录，校验结束后清理临时文件。
- 在审计事件中记录本次隔离文件名，方便排查上传安全决策。

## 修改文件

- `api/config.py`
- `api/.env.example`
- `api/utils/upload_security.py`
- `api/middleware/upload_guard.py`
- `api/tests/test_upload_guard.py`

## 代码逻辑

- 新增 `UPLOAD_QUARANTINE_DIR=uploads/quarantine` 配置，默认与 Dockerfile 中已创建的 `/app/uploads/quarantine` 对齐。
- `quarantine_upload_part` 会为每个上传 part 生成安全文件名，写入隔离目录；文件名包含 request id、字段名和随机 UUID，避免用户文件名穿透路径。
- `UploadGuardMiddleware` 在 MIME、扩展名、大小和魔数校验前先写 quarantine 文件，再进行校验。
- 无论上传被放行还是拒绝，都会在 `finally` 中调用 `cleanup_quarantined_uploads` 删除临时隔离文件。
- 审计日志新增 `quarantine_file` 元数据，成功和拒绝路径都能看到本轮临时隔离文件名。

## 对应功能

- 上传文件不再只停留在内存扫描流程中，而是具备明确的临时隔离落点。
- 被拒绝上传也会留下审计线索，包括拒绝原因和隔离文件名。
- 下游接口仍按原 multipart 请求读取文件，业务响应不变。

## 验证结果

- `python -m pytest api\tests\test_upload_guard.py -q`：9 passed。

## 风险与说明

- 当前实现按“临时隔离”处理，校验完成后立即清理文件，不长期留存恶意样本。
- 如果后续需要安全团队复盘样本，可在配置层增加“拒绝文件保留”开关，但本轮为了避免存储膨胀和敏感文件落盘，默认不保留。
