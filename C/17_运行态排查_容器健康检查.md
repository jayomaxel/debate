# 运行态排查：容器健康检查

## 本轮目标

继续验证工作包 C 的 Docker 运行态，确认当前阻塞是否来自代码、容器探活配置，还是本地环境状态。

## 修改文件

- `api/config.py`
- `docker-compose.yml`

## 修改逻辑

- `api/config.py`
  - 让 `ALLOWED_ORIGINS` 同时兼容两种环境变量格式：
  - 逗号分隔字符串，如 `http://localhost:8860,http://127.0.0.1:8860`
  - JSON 数组字符串，如 `["http://localhost:8860","http://127.0.0.1:8860"]`
  - 这样 Docker Compose 传入普通字符串时，API 不会在配置解析阶段提前崩溃。
- `docker-compose.yml`
  - 将 `web` 服务健康检查地址从 `http://localhost/healthz` 改为 `http://127.0.0.1/healthz`
  - 原因是容器内 `wget localhost` 会优先命中 IPv6 的 `::1`，而当前 Nginx 实际监听可用的是 IPv4 回环地址，导致服务真实可用但健康检查持续失败。

## 对应功能

- API 容器可以正确读取 CORS 来源配置并完成启动。
- Web 容器的健康检查与真实运行状态保持一致，不再出现“页面能访问但容器标记 unhealthy”的假失败。

## 本轮验证

- `docker logs debate-api --tail 200`
  - API 已完成启动、数据库初始化、Redis 初始化，`/health` 返回 `200 OK`
- `docker exec debate-api sh -c "curl -fsS http://127.0.0.1:7860/health"`
  - 返回数据库与 Redis 均已连接的健康结果
- `docker exec debate-web sh -c "wget -S -O- http://127.0.0.1/healthz"`
  - 返回 `200 OK`
- `curl http://127.0.0.1:8860/healthz`
  - 宿主机可直接访问网关健康检查
- `curl http://127.0.0.1:8860/api/health`
  - 宿主机经由 Nginx 代理访问 API 健康接口成功

## 结论

- 当前已确认的代码级运行态问题有两个：
  - `ALLOWED_ORIGINS` 解析失败
  - `web` 健康检查误探活到 `localhost(::1)`
- 另有一个需要注意的环境前提，不属于本轮代码缺陷：
  - 根目录 `docker-compose.yml` 设计为配合 `--env-file .env.deploy` 使用，默认的 `change-me-before-deploy` 只是占位值
  - 如果本机已经存在历史 `debate_pgdata` 卷，又直接执行不带环境文件的 `docker compose up`，会因为数据库卷中的真实密码与占位密码不一致而触发认证失败
  - 本地开发联调应优先使用 `docker-compose.dev.yml` 或 `docker-compose.local.yml`
